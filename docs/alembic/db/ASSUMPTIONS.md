## Assumptions & Judgment Calls

### 1. **pgcrypto Extension Required**
   - **SQL files don't explicitly create it**, but tables use `gen_random_uuid()` which requires it  
   - **Decision:** Added `CREATE EXTENSION IF NOT EXISTS pgcrypto` to migration 0001 upgrade()
   - **Rationale:** Without pgcrypto, `gen_random_uuid()` would fail at runtime

### 2. **Extensions Order in 0001**
   - Placed extensions first in upgrade() to ensure they're available when tables are created
   - Order: vector → pg_trgm → pgcrypto (though order doesn't matter here)

### 3. **Async Engine Configuration**
   - **env.py** uses `create_async_engine()` with `poolclass=pool.NullPool`
   - **Rationale:** NullPool is recommended for migrations (avoid connection starvation); production may want `QueuePool`
   - **Database URL:** Read from `DATABASE_URL` environment variable (no hardcoding in alembic.ini)

### 4. **HNSW Vector Index**
   - Migration uses `postgresql_using="hnsw"` with `vector_cosine_ops`
   - **Note:** Requires pgvector version with HNSW support (>= 0.5.0)
   - If deployment has older pgvector, consider falling back to IVFFLAT or changing the index strategy

### 5. **Trigger Function: search_vector_update**
   - Translated exactly from SQL: `destinations_search_vector_update()` with English tsvector
   - Uses raw `op.execute()` (Alembic has no first-class helper for plpgsql)

### 6. **set_updated_at Trigger**
   - Applied to: users, user_preferences, raw_scrapes, destinations, listings
   - **Not applied to:** user_interactions, itineraries, tags
     - These have no auto-update need (user_interactions is append-only; itineraries are created once)
     - tags has no updated_at column at all
   - Implemented via raw `op.execute()` for consistency

### 7. **CHECK Constraints in Migration 0002**
   - Used `op.execute()` instead of `op.check_constraint()` 
   - **Rationale:** Ensures exact SQL matches original file; easier to reason about in downgrade
   - Note on listings status: SQL says `'pending'`, NOT `'draft'` (matches 002 exactly)

### 8. **Partial Unique Indexes**
   - `idx_destination_images_one_primary` and `idx_listing_images_one_primary` use `WHERE is_primary`
   - Prevents multiple primary images per destination/listing
   - Implemented with `postgresql_where=sa.text("is_primary")`

### 9. **Downgrade Strategy**
   - **Migration 0001 downgrade:** Drops all 9 tables + triggers + extensions (complete rollback)
   - **Migration 0002 downgrade:** Drops only images tables, removes only columns added in 0002, drops only triggers added in 0002, keeps all 0001 objects intact
   - **Rationale:** Allows independent downgrade of schema hardening without losing initial schema

### 10. **DEFAULT Clauses for Booleans & INTs**
   - `destination_images.is_primary` → `DEFAULT false`
   - `destination_images.sort_order` → `DEFAULT 0`
   - `listings.currency` → `DEFAULT 'USD'`
   - All match the SQL file exactly

### 11. **NUMERIC Type for Ratings**
   - `listings.rating` uses `NUMERIC(2, 1)` (matches SQL)
   - This allows values like 1.0, 4.5, 9.9
   - `listings.price_amount` uses `NUMERIC(10, 2)` for currency amounts

### 12. **Foreign Key Cascade Behavior**
   - Destination deletions cascade to: listings, user_interactions, itineraries, tags
   - Listing deletions cascade to: user_interactions (SET NULL for some), listing_images
   - User deletions cascade to: user_preferences, user_interactions, itineraries
   - Matches the SQL exactly

### 13. **Metadata Import in env.py**
   - Imports `Base.metadata` from `app.db.base` with a try/except fallback  
   - If module doesn't exist, sets `target_metadata = None` (fine for hand-written migrations)
   - **Note:** For autogenerated migrations to work later, models must inherit from `Base`

### 14. **String Types for UUIDs**
   - Uses `postgresql.UUID(as_uuid=True)` throughout
   - Ensures server-side default of `gen_random_uuid()`

### 15. **No Offline Mode**
   - `run_migrations_offline()` is implemented but not used
   - Async + offline mode is complex; online mode is recommended for asyncpg

## Verification Steps

**Before running migrations:**
1. Set environment variable: `export DATABASE_URL="postgresql+asyncpg://user:pwd@host/dbname"`
2. Ensure PostgreSQL 15+ is running
3. Install dependencies: `pip install sqlalchemy[asyncio] asyncpg alembic pgvector`

**Run the round-trip test:**
```bash
cd backend/

# 1. Upgrade to latest
alembic upgrade head

# 2. Check current revision
alembic current
# Expected output: 0002

# 3. Downgrade to empty
alembic downgrade base

# 4. Upgrade again
alembic upgrade head

# 5. Final check
alembic current
# Expected output: 0002
```

**Expected schema after `upgrade head`:**
- 9 tables (users, user_preferences, raw_scrapes, destinations, tags, destination_tags, listings, user_interactions, itineraries, + 2 image tables)
- 3 extensions (vector, pg_trgm, pgcrypto)
- 1 trigger function (destinations_search_vector_update)
- 1 trigger function (set_updated_at) with 5 triggers
- ~20 indexes
- 7 CHECK constraints
- All columns and foreign keys as per SQL files

## Known Limitations / Future Considerations

1. **HNSW Index Availability:** If pgvector doesn't support HNSW, migration will fail. Fallback: change to `ivfflat` or remove distance-based indexing.

2. **Upgrade Safety:** The migrations are one-way in the sense that downgrading production data requires a backup. Always test in dev/staging first.

3. **Direct Raw SQL Bypass:** If someone runs the .sql files directly against the database (instead of via Alembic), Alembic's version table won't be updated. Always use migrations.

4. **Async Complications:** If transitioning to sync SQLAlchemy later, env.py will need refactoring (remove asyncio.run, use synchronous engine).

5. **Model Generation:** Once ORM models are defined in `app/models/`, they should inherit from `app.db.base.Base` so future autogenerated migrations work.
